# План: перевод загрузки скриптов на `sme::error::Error`

## Цель и границы

Перевести ошибки, возникающие при загрузке и подготовке скрипта, с `sme::RError` на структурированный `sme::error::Error`, не используя исключения `RError` для передачи ошибок.

В этот конвейер входят:

1. чтение файла и препроцессинг;
2. лексический анализ;
3. разбор в AST;
4. компиляция AST в функции/байткод;
5. публичные `Engine::load` и `Engine::loadSource`, которые связывают этапы.

Объём этой работы ограничен загрузкой и компиляцией. Не менять обработку runtime-ошибок и не подключать её к сбору ошибок загрузки/компиляции.

## Текущее состояние

- Публичный `Engine::load` и `loadSource` возвращают `void`. Ошибки препроцессора, парсера и компилятора доходят до вызывающего кода через `throw RError`.
- Текущие публичные объявления находятся в `include/sme/sme_engine.h`; их потребуется изменить вместе с реализациями в `src/sme_engine.cpp` и всеми вызовами.
- `PreprocessFile`, `PreprocessSource`, `lex`, `parse` и `compile` также используют исключения как способ остановить конвейер.
- В `rememberLiteral` препроцессор ловит `RError` лексера и заменяет его на более общий текст об ошибочном `#def`. Это место нужно сохранить семантически, но передавать ошибку структурированно и не терять исходную причину/позицию.
- `sme::error::Error` уже хранит `Code`, сообщение, `Location` и стек.
- В `error::Code` есть коды для большинства ожидаемых причин на каждом этапе, включая препроцессинг, лексер, парсер и компилятор.

## Предлагаемая модель передачи ошибки

Ошибки загрузки и компиляции возвращаются вызывающему коду; runtime не является частью этой миграции:

- `load` и `loadSource` возвращают `std::optional<error::Error>` непосредственно по значению. Пустой optional означает, что загрузка и компиляция прошли успешно; заполненный содержит первую обнаруженную ошибку.
- Предлагаемые публичные сигнатуры:
  - `std::optional<error::Error> Load(const std::string& path);`
  - `std::optional<error::Error> LoadSource(std::string_view source, std::string_view name = "script");`
- Пример вызова: `auto error = engine.LoadSource(source); if (error) { ... }`.
- Не добавлять отдельный `bool` и выходной параметр: пустой optional однозначно задаёт статус.
- Каждый этап возвращает отдельный результат, содержащий данные этого этапа и его диагностики. Ошибки не помещаются внутрь элементов данных: не добавлять ошибки в `Token` или `Program`.
- Результаты этапов: `SourceUnit` содержит результат препроцессинга и optional ошибки; `LexResult` содержит `std::vector<Token>` и optional ошибки лексера; `ParseResult` содержит `Program` и optional ошибки парсера; результат компиляции содержит функции/чанки и optional ошибки компилятора.
- `Engine::load`/`loadSource` передают вызывающему коду первую ошибку этапа, который завершился неуспешно.
- Если этап обнаружил ошибку, немедленно завершить его и весь конвейер: не искать дополнительные ошибки и не запускать следующий этап.
- После ошибки загрузки/компиляции Engine считается непригодным; скрипты на нём запускать нельзя. Откат уже изменённых внутренних данных не требуется — вызывающая сторона должна считать такой Engine сломанным и не использовать его.
- Не оборачивать этапы общим `catch (...)`: ожидаемые ошибки должны создаваться в месте возникновения. Отдельно решить и документировать поведение действительно неожиданных исключений стандартной библиотеки; не превращать их в успешный результат или произвольную ошибку скрипта.

## План работ

### 1. Зафиксировать контракт API загрузки

- Изменить публичные объявления в `include/sme/sme_engine.h`: `load` и `loadSource` возвращают `std::optional<error::Error>` вместо `void`.
- Синхронно изменить определения методов в `src/sme_engine.cpp` и все вызовы этих методов по проекту.
- Пустой optional означает успех; заполненный — ошибка. Не дублировать этот результат отдельным `bool`.
- Не связывать результат загрузки с обработчиками или механизмами runtime-ошибок.
- Обновить все вызовы и тесты публичного API, в том числе места, которые ранее рассчитывали на исключение.

### 2. Согласовать вспомогательные типы ошибок

- Проверить и заполнить коды для всех фактических ошибок загрузки; не переиспользовать общий код, если каталог уже содержит точную причину.
- Устранить расхождения между каталогом `Code` и реально возникающими сообщениями. Особое внимание: ошибки открытия/чтения файла, malformed `#include`/`#def`, ошибки литералов и внутренние ошибки компилятора.
- Сформировать `Location` в точке ошибки: имя фактического файла/исходника и строка. Ошибки без известной строки оставляют `line == 0`.
- Для ошибок вложенного `#include` сохранять путь того файла, где ошибка реально произошла. Если для диагностики важен путь включений, передавать его отдельной цепочкой кадров/контекстом, не подменяя `source`.
- На этапе загрузки `function`, `instruction` и VM stack обычно неизвестны; оставлять эти поля пустыми, а не придумывать значения.

### 3. Перевести лексер и препроцессор

- Заменить `throw RError` в `lex` и `PreprocessFile`/`PreprocessSource` на результаты с диагностикой `error::Error`.
- Передать ошибки препроцессора в `SourceUnit`; если препроцессор вернул хотя бы одну ошибку, прекратить загрузку и не запускать лексер.
- Добавить `std::optional<error::Error>` в `SourceUnit` для первой ошибки препроцессора.
- Изменить `lex` так, чтобы он возвращал `LexResult` с токенами и optional первой ошибки. Ошибка может не соответствовать ни одному токену, поэтому не прикреплять её к `Token`.
- В `rememberLiteral` сохранить связь ошибки лексера с контекстом `#def`: добавить контекст к исходной диагностике, не теряя код причины и известные координаты.
- Удалить `catch (const RError&)` в этой цепочке после перехода соответствующего API на результат.
- Не менять раскрытие макросов, порядок `#include`, правила комментариев и поведение корректных скриптов.

### 4. Перевести парсер и компилятор

- Изменить `parse` так, чтобы он принимал результат лексера и возвращал `ParseResult`, содержащий `Program` и `std::optional<error::Error>`.
- Не помещать диагностики в `Program`: AST остаётся только представлением программы, а ошибки принадлежат результату разбора.
- Останавливать парсер при первой ошибке; после ошибки компилятор не запускать.
- Перевести `compile` и функции компилятора на результат, содержащий скомпилированные функции и `std::optional<error::Error>`; при первой ошибке прекратить компиляцию.
- Если лексер или парсер вернул ошибку, следующий этап не запускается. Если компилятор вернул ошибку, загрузка завершается неуспешно.
- Проверить ранние выходы и частично собранные AST/Chunk: временные значения освобождаются обычным RAII.

### 5. Сделать `Engine::load`/`loadSource` точкой возврата ошибок

- Собрать конвейер из возвращающих результат стадий: preprocess → lex → parse → compile.
- Передать первую ошибку этапа вызывающему коду и завершить pipeline; вернуть `std::nullopt` только при успешном завершении всего конвейера.
- Удалить `RError` из веток загрузки и проверки активного вызова; последнюю преобразовать в `ENGINE_LOAD_DURING_ACTIVE_CALL`.
- Сохранить существующий `SME_ASSERT` для обязательной файловой системы; ошибки чтения/открытия файла передавать через `error::Error`.
- При ошибке завершить загрузку и вернуть первую ошибку; Engine считается непригодным, скрипты после такой ошибки запускать нельзя. Не проектировать откат/восстановление Engine в рамках этой задачи.
- Сохранить существующую семантику успешной повторной загрузки: старые глобалы сохраняются, значения `#def` с тем же именем обновляются, таблица функций заменяется.

### 6. Удалить `RError` только из области загрузки

- После перевода этапов выполнить поиск `RError` в препроцессоре, лексере, парсере, компиляторе и загрузочной ветке `Engine`.
- Не удалять класс `RError` из проекта, если он ещё используется вне загрузки и компиляции.
- Обновить комментарии и документацию, если они описывают исключения как контракт `load`/`loadSource`.

### 7. Проверки и критерии готовности

- Для каждого этапа добавить тесты, проверяющие код ошибки, `message`, `Location.source` и `Location.line`.
- Проверить ошибки из основного файла и вложенного include, включая некорректный `#def` и синтаксическую ошибку после препроцессинга.
- Проверить, что каждый этап возвращает только первую ошибку и последующий этап не запускается.
- Проверить, что при ошибках препроцессора лексер, парсер и компилятор не запускаются; при ошибках лексера парсер и компилятор не запускаются; при ошибках парсера компилятор не запускается.
- Проверить, что загрузка возвращает `std::nullopt` при успехе и ошибку при неуспехе; последовательные вызовы не смешивают диагностики, поскольку каждый вызов возвращает свой результат.
- Проверить, что `RError` не выбрасывается из загрузки.
- Проверить успешные `load` и `loadSource`, повторную загрузку и существующие тесты языка.
- Запустить полный Debug build/test. Затем поискать все `throw RError` в перечисленных загрузочных файлах и вручную подтвердить, что оставшиеся в проекте выбросы относятся только к runtime/API вне согласованных границ.

## Основные риски

- Замена публичных сигнатур `void load/loadSource` на возврат `std::optional<error::Error>` меняет API Engine и требует синхронно обновить объявления, реализации, вызовы, тесты и примеры.
- Этапы останавливаются на первой ошибке. Следующие этапы после любой ошибки не запускаются.
- После ошибки Engine считается сломанным; вызывающий код не должен запускать на нём скрипты и должен отбросить этот экземпляр.
- Каталог кодов может содержать похожие, но не соответствующие текущей диагностике причины; механическая замена строк на коды даст неточные ошибки.
- Интерфейс файловой системы различает отсутствие файла через null handle, но `IFile::Read` использует `0` как конец потока; возможность сообщить отдельную ошибку чтения ограничена текущим API. Если нужно гарантировать различение EOF и read failure, это следует оформить отдельным решением, а не скрывать в миграции компилятора.
