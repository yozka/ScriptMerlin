# План: удаление `RError` и структурированная обработка runtime-ошибок

## Цель и границы

Полностью удалить класс `sme::RError` и перевести ошибки выполнения и ошибки публичного API на структурированный `sme::error::Error`.

Миграция включает:

- исполнение байткода в VM;
- вызовы `Engine::call`, `callIndex` и `resume`;
- нативные функции, встроенные библиотеки и пользовательские `IScriptObject`;
- проверку аргументов/состояния в публичных методах Engine;
- доставку runtime-ошибки в `error::IHandler`;
- тесты, примеры и документацию, использующие `RError` или предполагающие исключение.

Ошибки загрузки и компиляции уже возвращаются через `error::Error::Opt`. Их контракт не менять и не объединять с runtime API иначе, чем повторным использованием типа `error::Error`.

## Наблюдаемое текущее поведение

- VM выбрасывает `RError` из арифметики, операторов, исполнения инструкций, доступа к индексам/свойствам, управления кадрами и других проверок. В большинстве таких случаев известна строка инструкции.
- `Engine::invoke` и `Engine::resume` ловят только `RError`, пишут `what()` в лог, затем повторно выбрасывают исключение. RAII guard в `Machine::run`/`resume` снимает соответствующий `RunState` при исключении.
- `Engine::RuntimeError(code, text)` передаёт ошибку в `State::RuntimeError`, а тот вызывает `IHandler::Handle`, если обработчик задан. Этот путь сам не останавливает VM и не возвращает ошибку вызывающему коду; вызывающая native-функция обычно после него самостоятельно возвращает `Value::Null()`.
- `IScriptObject` и `NativeFn` сейчас возвращают обычный `Value` и могут сообщать о неуспехе исключением либо через `RuntimeError`.
- Помимо собственно runtime есть проверки API (`call`, `callIndex`, `resume`), которые тоже выбрасывают `RError`. Их также нужно учесть, чтобы действительно удалить тип целиком.

## Предлагаемый целевой контракт

1. Хранить последнюю runtime-ошибку в `State` как `error::Error::Opt`; `Engine` предоставляет методы-запросы к этому состоянию, но не дублирует у себя ошибку.
2. Добавить публичные методы `Engine::HasError() const` и `Engine::LastError() const`: первый сообщает о наличии runtime-ошибки, второй возвращает последнюю ошибку (`error::Error::Opt`).
3. Ошибка из VM или `Engine::RuntimeError` останавливает текущий script execution. Запуск возвращает `Value::Null()` при ошибке; вызывающий код отличает этот случай от нормального null через `HasError()` и получает детали через `LastError()`.
4. `State` сохраняет ошибку до вызова `IHandler::Handle`; после уведомления она остаётся доступной через запросы Engine. Без handler ошибка также хранится и доступна.
5. Не менять контракт `NativeFn` и `IScriptObject`: callbacks сохраняют текущие return types и при необходимости вызывают `engine.RuntimeError(code, text)`. Этот вызов сохраняет ошибку в `State`, уведомляет handler и помечает активное выполнение ошибочным; после возврата callback VM останавливает скрипт.
6. Перед началом нового верхнеуровневого запуска предыдущая ошибка очищается. `resume` и вложенные вызовы в рамках активного выполнения её не очищают.
7. Не перехватывать общим `catch (...)` неожиданные исключения пользовательского кода, ошибки выделения памяти и дефекты программы. Ожидаемые ошибки скрипта проходят через структурированный runtime-путь.
8. Ошибки неправильного использования публичного API Engine также перевести с `RError` на структурированные ошибки/результаты; они не должны записываться в `State` как последняя runtime-ошибка, если не относятся к выполнению скрипта.

## План миграции

### 1. Зафиксировать модель хранения и доставки ошибки

- Добавить в `State` поле последней ошибки runtime типа `error::Error::Opt`.
- Добавить методы `Engine::HasError() const` и `Engine::LastError() const`; оба читают состояние из `State`, не храня собственную копию.
- `HasError()` сообщает, записана ли runtime-ошибка; `LastError()` возвращает копию `error::Error::Opt`, чтобы ошибка оставалась безопасной после возврата из метода.
- Сохранить публичный return type `Value` у `call`, `callIndex` и `resume`; на runtime-ошибке возвращать `Value::Null()`, а наличие ошибки проверять отдельно.
- При начале нового верхнеуровневого запуска очищать прошлую ошибку в `State`. Не очищать её в `resume` и при вложенном вызове из native-функции.
- Сначала сохранить ошибку в `State`, затем вызвать handler ровно один раз. Handler — уведомление, не место хранения и не замена getters.

### 2. Завести точные коды и диагностические данные

- Сопоставить существующие runtime-ошибки с `error::Code`: переполнение, деление на ноль, сдвиг, несовместимые типы, неверный индекс, dangling reference, ошибки рекурсии/call depth, некорректное состояние VM и прочее.
- Использовать уже существующие коды, где они точно соответствуют причине; добавить коды для оставшихся причин, не сводить разные сбои к `UNKNOWN` или одному общему коду.
- Передавать строку инструкции через `error::Location`, а не дописывать её к сообщению, как делал `RError`.
- Формировать `error::StackFrame` из `RunState`/`Frame` при распространении ошибки; сохранять исходный `sourceName` и не терять функцию и инструкцию при вложенных script-вызовах.
- Для ошибок API, где скриптового места нет, оставлять location пустым и использовать соответствующие `ENGINE_*` коды.

### 3. Перевести чистые runtime-помощники и VM

- Изменить арифметические helpers (`checkedInt*`, `intBinary`, `narrowInt`, `binary`, `unary`, `compare`, `materialize` и подобные) на передачу структурированной ошибки вверх без исключений.
- В `Machine::execute` при ошибке инструкции немедленно завершать выполнение; записать ошибку в `State` и не продолжать байткод после сбоя.
- Распространять ошибку без повторного создания/обёртывания, сохраняя исходные code, location и stack.
- Заменить исключительный выход в `Machine::run` и `resume` на явный статус выполнения. Сохранить RAII cleanup `RunState` при ошибке и проверить `return`, `stop`, вложенный `call`, callback, который вызывает `RuntimeError`, и ошибку при `resume`.
- После callback проверять сохранённый runtime-статус; если callback сообщил ошибку, прекратить VM сразу после его возврата, не исполняя следующую инструкцию.
- Удалить комментарии о снятии RunState «при исключении» и описать гарантии cleanup при runtime-ошибке.

### 4. Сохранить контракт native-функций и интерфейса объектов

- Не менять сигнатуры `NativeFn` и `IScriptObject`: нативные функции продолжают возвращать `Value`, методы объектов — свои текущие типы.
- Сохранить `Engine::RuntimeError(code, text)` как путь, которым native-функции и объекты приложения сообщают runtime-ошибку в `IHandler`.
- Не подменять явный вызов `RuntimeError` возвратом `error::Result` и не заставлять callback бросать исключение для уведомления обработчика.
- Изменить семантику `RuntimeError`: он записывает ошибку в State и уведомляет handler; после возврата из callback VM видит сохранённую ошибку, останавливает выполнение и не исполняет следующие скриптовые инструкции.
- Callback сохраняет текущий return type; его возвращаемое значение игнорируется VM, если за время callback была записана runtime-ошибка.
- Обновить только те реализации callback-ов, которые непосредственно бросают `RError`, чтобы они вызывали `engine.RuntimeError(...)`; VM остановит активный скрипт по сохранённому статусу.

### 5. Перевести Engine API и ошибки состояния

- Сохранить `Value` в качестве return type у `Engine::call`, `callIndex` и `resume`; runtime failure возвращает `Value::Null()`, а подробности доступны через `HasError()`/`LastError()`.
- Реализовать методы-запросы Engine как доступ к `State::lastRuntimeError`, не создавая вторую копию хранения.
- Очищать `State::lastRuntimeError` только перед новым верхнеуровневым запуском; `resume` и вложенный вызов не должны сбрасывать ошибку активного запуска.
- Решить API формы для `RegisterNative`, `RegisterFactory`, `bind`, `resizeTable` и других методов, сейчас бросающих `RError`: для операций без значения вернуть `error::Error::Opt`/`error::Result<void>`, для операций со значением — `error::Result<T>`. Ошибки этих API не записывать в `lastRuntimeError`, если нет ошибки активного скрипта.
- Для `findFunction`/`findGlobal` сохранить `std::optional<size_t>`: отсутствие имени в этих поисковых методах уже является штатным результатом, а не runtime-ошибкой.
- Перевести `Engine::invoke` и `Machine::run`/`resume` на распространение явного статуса; убрать `catch (const RError&)`, логирование `what()` и повторный `throw`.
- При VM-ошибке сохранить `Error` в State до вызова handler, вызвать handler один раз, очистить соответствующий RunState и вернуть `Value::Null()` из текущего запуска.
- Для ошибки, переданной callback-ом через `RuntimeError`, не вызывать handler повторно: ошибка уже сохранена и доставлена. VM только останавливает выполнение после возврата callback-а.
- Перевести `State::freshReferenceId`, `constantString` и остальные state helpers с `RError` на результат там, где ошибка может штатно возникнуть; определить точное поведение при исчерпании счётчика идентичности.

### 6. Удалить `RError` и завершить API-миграцию

- Найти все `throw RError`, `catch (const RError&)`, упоминания `RError` и использование `what()`/`line()` во всём проекте, включая заголовки, библиотеки, examples и tests.
- Удалить класс `RError` и больше не использовать исключения как штатный протокол runtime-ошибок.
- Не оставлять временный адаптер, который внутри снова бросает/ловит `RError`: он не удовлетворяет цели полного удаления.
- Обновить README и публичные комментарии, описав получение ошибки через результат и необязательное уведомление handler.

### 7. Тесты и критерии готовности

- Для каждого класса runtime-сбоя проверить точный `Code`, сообщение и `Location`; для VM-ошибок проверить порядок и содержимое stack trace на вложенных вызовах.
- Проверить, что одна runtime-ошибка останавливает скрипт, записывается в State, доступна через `HasError()`/`LastError()` и передаётся handler ровно один раз.
- Проверить вызов без handler: ошибка всё равно сохраняется в State и доступна через getters.
- Проверить, что callback вызывает `engine.RuntimeError`, handler получает ошибку, скрипт останавливается после callback-а, и последующие инструкции не выполняются.
- Проверить, что начало нового верхнеуровневого запуска очищает предыдущую ошибку; `resume` и вложенный вызов её не очищают.
- Проверить, что после ошибки `RunState` очищен; отдельные тесты для вложенных вызовов, рекурсии, `stop`/`resume` и ошибки внутри вложенного вызова.
- Проверить ошибки публичного API: пустой callback/factory, неизвестная функция, вызов неверного индекса, `resume` без остановленного скрипта, неверный объект таблицы.
- Проверить, что корректные скрипты сохраняют результат, а существующие runtime-тесты обновлены только с учётом нового API, не меняя семантику языка.
- Выполнить поиск по проекту и подтвердить отсутствие символа/текста `RError`, `throw`/`catch` для штатных runtime-ошибок и логирования `what()` из старой схемы.
- Запустить полный Debug build/test; затем выполнить Release build/test, если она является поддерживаемой конфигурацией проекта.

## Основные риски и границы

- Это публичное source/API breaking change: изменятся return types `call`/`callIndex`/`resume` и, вероятно, регистрации/мутации Engine. Сигнатуры `NativeFn` и `IScriptObject` остаются прежними.
- Преобразование VM с исключений на результат затронет множество внутренних функций; нельзя пропускать ошибку и продолжать исполнение с фиктивным `Value::Null()`.
- Stack trace нужно собирать до очистки кадров; при этом очистка состояния обязана выполняться и при обычной ошибке, и при `stop`.
- State хранит последнюю runtime-ошибку; Engine предоставляет только методы чтения; handler получает уведомление после сохранения. Ошибка VM и ошибка, переданная через `RuntimeError`, обе останавливают текущий скрипт.
- Ошибки из пользовательского C++ кода, не использующего API `error::Result`, не должны автоматически превращаться в скриптовые ошибки. Исключения этого кода остаются непредвиденными исключениями и могут распространяться как таковые.
- Нельзя изменять семантику скриптового языка или правила препроцессинга/компиляции в рамках этой runtime-миграции.
