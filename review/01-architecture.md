# Архитектура

## Конвейер

```
.gs → preprocess (директивы, литералы) → lex → parse (AST) → compile (Chunk) → Machine
```

| Слой | Файлы | Роль |
|------|--------|------|
| Препроцессор | `src/preprocess.cpp` | `#include`, `#def`, `#ifdef`, `#scope`, литералы в `SourceUnit` |
| Лексер | `src/lexer.cpp` | Токены + **отдельные токены Newline** (значимые для синтаксиса) |
| Парсер | `src/parser.cpp` | Рекурсивный спуск, `Program` = globals + functions |
| Компилятор | `src/compiler.cpp` | Один проход collect (locals) + codegen в регистры |
| VM | `src/machine.cpp`, `src/state.h` | Интерпретация `Instruction`, heap + GC |
| API | `src/engine.cpp` | Natives, load/call, gs_* библиотека |

## Что сделано удачно

1. **Чёткое разделение** compile-time (AST/Chunk) и run-time (Machine/Heap). Публичный API узкий (`include/sme/engine.h`).
2. **Регистровая модель** с двухфазной компиляцией функции: сначала `collect()` объявляет все locals (включая неявные из присваиваний), потом `watermark_` фиксирует размер кадра — предсказуемый `registerCount`.
3. **Ссылки (`Reference`)** на слоты кадра/глобал/элемент таблицы — осознанная модель для out-параметров (`&x`, `*x`), согласована с тестами `test_language.gs`.
4. **Препроцессор отделён от парсера** — legacy-совместимость с макросами `TYPE_*`, `#def` без усложнения грамматики.
5. **Тесты как спецификация** — отдельные кейсы вроде `test_NoShortCircuit` явно кодируют семантику.

## Слабые места архитектуры

### 1. «Большой комок» AST

`Expr` и `Stmt` — одна структура на все варианты (`kind` + поля + `kids`). Это быстро писать, но:

- легко забыть заполнить поле;
- `Expr::Kind::Bool` в enum есть, парсер почти всегда кладёт `true`/`false` в `Kind::Int`;
- нет визитора — везде `switch (kind)`.

**Упрощение (позже):** `std::variant<...>` по узлам или отдельные типы + `unique_ptr<ExprBase>`.

### 2. Дублирование ответственности за комментарии

- `preprocess.cpp` — `stripComments()` для директив.
- `lexer.cpp` — снова `//` и `/* */`.

Для `load()` текст уже без комментариев из препроцессора; для `loadSource()` без препроцессора — только лексер. Два пути, два поведения (например, `#` в сыром тексте).

### 3. Поиск по имени в рантайме

- `CallName` в `machine.cpp` — **линейный** `find_if` по `state().functions` и `nativeNames` на каждый динамический вызов.
- `Engine::call` / `findFunction` — то же.

Для скриптов с `call(gid)` из `test_script.gs` это может быть узким местом. На этапе `compileUnit` уже есть `unordered_map` для globals/natives — для функций скрипта карту не строят.

### 4. Два стека ограничений рекурсии

- `runStack.size() >= 64` в `Machine::run`;
- `frames.size() > 256` в `execute()`.

Разные лимиты, разная семантика ошибки — путаница для отладки.

### 5. GC «по счётчику»

`Heap::kCollectAt = 32` — попытка сборки, когда слотов уже ≥ 32 и свободных нет; после неё куча всё равно растёт. Агрессивно для мелких скриптов, непрозрачно для автора нативов (когда вызывается `HostObject::release`).

`vector<unique_ptr<Slot>>` трогать не стоит: адреса слотов должны пережить `push_back`, на них опираются `Object&` и элементы таблиц. Плоский `vector<Slot>` это сломает.

## Дополнение

### Два входа в VM

| Вход | Арность | Стек | Сборка мусора |
|------|---------|------|----------------|
| `Op::Call` из скрипта | лишние аргументы отбрасываются, недостающие остаются `null` | кадр в текущем `RunState`, лимит 256 | по счётчику кучи |
| `Machine::run` (`Engine::call`, `callIndex`) | число аргументов обязано совпасть | новый `RunState`, лимит 64 | `call` собирает кучу на каждом возврате, `callIndex` нет |

Один и тот же `fn paint(x)` из скрипта вызывается как `paint()` и подставляет значение по умолчанию, а `engine.call("paint")` бросает `wrong number of arguments`. Натив `call(fid)` идёт через `callIndex`, то есть через строгий путь.

`Op::Call` ещё и не проверяет лимит 64. Рекурсия скрипт→скрипт и реентерабельность хост→`call`→скрипт — разные счётчики. Это уже отмечено выше; дополнение в том, что у них разная арность и разная политика ошибок.

### Корни GC и время жизни значения у хоста

`gatherRoots` видит глобалы, регистры кадров и `pins`. Не видит:

- `Value` на стеке C++ (аргументы натива, результат `call` после `pins.pop_back()`);
- поля внутри `HostObject`, если хост сам держит `Value`.

`Engine::call` пинит результат, собирает кучу (поэтому `HostObject::release` срабатывает до возврата в игру — на это завязан `test_PropRelease`) и сразу снимает пин. Хендл жив до следующей сборки. Следующий `call` собирает всегда: повторный `toString` предыдущей строки даёт `"null"`, потому что мёртвый хендл в `typeName` тоже называется `"null"`. Отличить «скрипт вернул null» от «хендл уже собран» нельзя.

`anchor` / `clearAnchors` — единственный способ удержать значение между вызовами, но `clearAnchors` обнуляет весь вектор. `strexplode` вызывает его в конце. `makeTable` рядом делает правильно: запоминает `pins.size()` и обрезает до этой отметки.

### `load` не является перезагрузкой

`compileUnit` подменяет `functions` целиком. Глобалы только дописываются (`addGlobal` выходит, если имя уже есть), поэтому повторный `int hp;` не сбрасывает ни тип, ни значение. `#def` через `literals` значение перезаписывает. Нативы, фабрики, `pins` и `runStack` не трогаются. `load` поверх поставленного на паузу или упавшего кадра оставляет старые кадры смотреть в новую таблицу функций.

`#scope` — одно число на весь `SourceUnit`, его копируют во все чанки. `functionScope` читается как «область функции», по факту это область файла. Тест `Language.Scope` фиксирует: и `test_LangInclude`, и `lang_included` получают `41`.

### Мёртвые крючки

- `useFileSystem` сохраняет указатель, дальше его никто не читает. `load` и `#include` открывают файлы через `ifstream` / `std::filesystem`.
- `useLog` подключён только к `State::fail`, а `fail` не вызывается. Ошибки языка — голый `throw Error`, в лог они не попадают.
- `platformName()` в репозитории не вызывается. Шесть платформенных `.cpp` отличаются одной строкой. Пока слой не делает ввод-вывод, наращивать его незачем; публичный символ при этом может быть нужен игре снаружи.

### Лишний include

`src/ast.h` включает `state.h`, но узлам AST типы VM не нужны. Из-за этого парсер тянет `engine.h`. Include можно убрать.
