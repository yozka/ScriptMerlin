# Баги, мёртвый код, риски

## Подтверждённые / высокая уверенность

### 1. Мёртвый опкод `Op::Passed`

Реализован в `machine.cpp` (`ins.b < frame.supplied`), но **нигде не эмитится** из `compiler.cpp`. Мёртвый код + ложная модель для читателя `?param`.

**Исправление:** либо подключить в `compilePassed` для параметров текущей функции, либо удалить опкод и переименовать AST `Passed` → `TypeofQuery`.

### 2. Глобальные `type name = expr;` не работают

См. `parseGlobalDecl` — инициализатор отбрасывается. Либо убрать синтаксис из грамматики (ошибка «инициализаторы только через #def»), либо сохранять AST и генерировать `StoreGlobal` в entry chunk / static init.

### 3. Hex/binary литералы без проверки переполнения int32

В `scanNumber` для `0x...` значение копится в `uint32_t` и кастуется в `int32_t` без проверки диапазона (десятичные проверяют). `0xFFFFFFFF` станет `-1` молча.

### 4. `Move` / `StoreGlobal` / `StoreRef` пропускают присвоение `null`

```585:590:src/machine.cpp
        case Op::Move: {
            Value incoming = reg(...);
            if (!std::holds_alternative<std::monostate>(incoming)) {
                write(ins.a, std::move(incoming));
            }
```

Инструкция не пишет слот, если входящее значение — `null`, и оставляет прежнее содержимое. `SetIndex` и `Return` так не делают: элемент таблицы обнуляется, результат функции хосту отдаётся. Временные регистры между операторами не чистятся, поэтому в слоте оказывается значение предыдущего оператора, а не «старая переменная». Прогон — в дополнении.

### 5. `callIndex` при неверном индексе возвращает `0`

```438:442:src/engine.cpp
    if (index < 0 || ...) {
        return integer(0);
    }
```

Тихий сбой вместо `Error` — опасно для host-кода.

## Риски (дизайн / краевые случаи)

### Ссылки на locals после выхода из функции

`Reference` хранит индекс кадра, без поколения. GC метит контейнер только у indexed-ссылки. Пока стек короче сохранённого индекса, `*ref` кидает `dangling reference`. Как только новый вызов занимает тот же индекс, ссылка молча читает чужой регистр. Прогон — в дополнении.

### Сравнение чисел как double

`equals` для чисел сравнивает через `double`. Большие int32 могут совпасть неверно с float — классическая проблема; для игрового DSL часто приемлемо, но стоит знать.

### `GetIndex` для строк vs таблиц

Разное поведение типа результата (строка-символ vs элемент). Ошибки «index out of range» vs пустой символ — согласованы с тестами, но не с интуицией C.

### Препроцессор: `#ifdef` без `#endif`

Однострочная модель: следующая непустая строка — ветка. Легко сломать при многострочных блоках; нет `#else`. Документировать как «макро-язык 1.0».

### Дублирование `abs` / `gs_abs` / math library

Три слоя математики (`addMathLibrary`, `installGsLibrary`, нативы в тестах). Риск расхождения поведения.

### Несогласованность `typeCode` и `typeof` в скрипте

`Engine::typeCode`: pointer → 6, ref/null → 0. Скриптовый `typeof` через native `type` возвращает **строку** (`typeName`), а `?x` — код. В `test_script.gs` сравнение с `TYPE_INT` — из препроцессора. Хрупкая связка.

## Лексер / парсер

### `group_` / `braceExpr_` в `peek()`

Счётчики скобок, чтобы игнорировать newline внутри `(...)`, `[...]`, `{...}` в выражениях. Работает, но хрупко: легко забыть `account()` при новом токене; альтернатива — склеивать newline в пробел на уровне лексера внутри групп (один механизм).

### Held-token в лексере для newline

Два вызова `next()` на одну «логическую» позицию. Усложняет отладку токен-стрима. Альтернатива: вставлять `Newline` в поток без hold.

### `spell()` в парсере

Возвращает `"token"` для большинства видов — слабые диагностики ошибок.

## Безопасность

- `Cast` с пользовательским `printf`-форматом: есть `safeFormat`, но подмножество ограничено — хорошо; всё равно следить за `%n` и размером буфера 128. `%s` в этом фильтре разрешён, но в `numberText` он не подставляет пользовательскую строку.
- `load` / `#include` читают диск через `ifstream` и `std::filesystem`. `useFileSystem` на этот путь не влияет, запрета `..` нет: кандидат ищется рядом с текущим файлом, в корне юнита и в `current_path()`.

## Дополнение: подтверждено прогоном

Скрипты ниже гонялись через `Engine::loadSource` на текущих исходниках. Полный `ctest` для этого прохода не запускался.

### 6. Пропуск `null` в `Move` портит соседние операторы

Три опкода выходят, не записав слот:

```585:590:src/machine.cpp
        case Op::Move: {
            Value incoming = reg(state().runStack.back().frames.back(), ins.b, ins.line);
            if (!std::holds_alternative<std::monostate>(incoming)) {
                write(ins.a, std::move(incoming));
            }
```

Та же проверка стоит в `StoreGlobal` и `StoreRef`. Кадр при входе забит `null`, но регистры выше локалов между операторами не обнуляются: `compileBody` только откатывает `watermark_`. Следующий оператор получает номер регистра, в котором ещё лежит результат предыдущего.

| Скрипт | Результат прогона |
|--------|-------------------|
| `x = 5; x = null; return x` | `5` |
| `x = 5; x = f();` при `return null` из `f` | `5` (`Return` в слот вызова null пишет, дальнейший `Move` в `x` — нет) |
| `var t = 1 + 2; return true ? null : 0` | `1` |
| `var t = 1 + 2; return id(null)` | `2` |
| `t = {7}; t[0] = null; return t[0]` | `null` (`SetIndex` пишет честно) |
| тот же элемент, `return typeof(t[0])` | `4` — код таблицы |

Последняя строка — самый показательный случай. Элемент уже `null`, но аргумент натива копируется через `Move`. В слоте аргумента остаётся таблица из предыдущего оператора, и `typeof` отвечает «table». Если временный регистр ещё ни разу не занимали, тот же вызов случайно возвращает `null`. От сюжета скрипта зависит, проявится ошибка или нет.

Починка одна: эти три опкода должны записывать `null` так же, как `LoadConst` и `SetIndex`. Обнулять временные регистры на каждый оператор — заплатка, она не чинит `x = null`.

### 7. Ссылка на локал переиспользует чужой кадр

```
int g;
fn leak() { var x = 42; g = &x; return 1; }
fn other() { var y = 7; return *g; }
```

| Вызов | Результат |
|-------|-----------|
| `main`: `leak(); return other();` | `7` |
| два отдельных `engine.call`: сначала `leak`, потом `other` | `7` |
| `leak(); return *g` без нового кадра поверх | `dangling reference` |

`MakeRefLocal` запоминает `frames.size() - 1` и слот. Поколения у кадра нет. Пока индекс больше текущей глубины, срабатывает проверка. Новый вызов (в том же `RunState` или следующим `Engine::call`, у которого свой кадр 0) занимает тот же индекс, и `LoadRef` читает `y`. GC ссылку не уничтожает: глобал `g` — корень, а регистр, на который она показывает, корнем уже не является.

Нужен монотонный id кадра в `Reference` и в `Frame`. Индекса в векторе недостаточно.

### 8. Исключение не снимает кадр, движок после этого мёртв

`Machine::run` пушит `RunState` и попадает в `finish` только при нормальном возврате из `execute`. `1 / 0` бросает `Error` мимо `pop_back`.

Прогон: 70 вызовов `boom` (`return 1 / 0`) дают 64 исключения `division by zero`, затем исключения `script call nested too deeply` (лимит `runStack.size() >= 64`). Следующий `ok`, который должен вернуть `3`, тоже получает `script call nested too deeply`.

Кадры зомби остаются в `gatherRoots`, их значения не собираются. Тот же `load` кадры не чистит.

Нужен guard вокруг `run` / `resume`: при исключении снять ровно тот `RunState`, который этот вызов положил. Чужую паузу ниже по стеку не трогать.

### 9. `call` во время `stop` теряет паузу

`finish` на обычном результате всегда пишет `suspended = false` и снимает только верхний `RunState`:

```260:267:src/machine.cpp
Value Machine::finish(std::optional<Value> result) {
    if (!result) {
        state().suspended = true;
        return null();
    }
    state().suspended = false;
    state().runStack.pop_back();
    return *result;
}
```

Прогон: `call("main")` со `stop` → `stopped == true`; затем `call("other")` возвращает `2` и выставляет `stopped == false`; `resume()` бросает `script is not stopped`. Нижний кадр с паузой остаётся в `runStack` навсегда, флаг уже не отражает стек.

`suspended` должен значить «верхний `RunState` стоит на `Stop`», и вложенный `call` не имеет права гасить чужую паузу.

### 10. Значение у хоста умирает на следующей сборке, `anchor` стирает `strexplode`

- `call` функции, которая возвращает `"hello-result"`, затем второй `call`: `toString` первого результата — `"null"`.
- `anchor(makeString("pinned-value"))`, затем `strexplode("a|b", 124)`: после возврата та же строка читается как `"null"`.

`strexplode` копит части через `anchor` и в конце вызывает `clearAnchors()`, который делает `pins.clear()`. Якоря хоста, поставленные до натива, пропадают. Сразу после этого `call` собирает кучу. `makeTable` уже умеет отрезать только свои пины (`pins.resize(mark)`). `strexplode` должен делать так же.

Пока хендл собран, `typeName` / `toString` говорят `"null"`, а не «висячий хендл». Порча выглядит как обычный null.

### 11. `#def` кладёт в глобал не то, что видит скрипт

`rememberLiteral` парсит значение сам: `stol(..., 0)`, `stof`, срез строки. Лексер тот же текст потом разбирает иначе. Цифры расхождения — в таблице раздела семантики. Дополнительно `#def N abc` бросает `std::invalid_argument` (`stol: no conversion`), не `sme::Error`: нет номера строки, хост, который ловит только `sme::Error`, это пропускает.

Тот же класс ошибок у литералов, которые `stol` / `stof` не дочитывают (`1+2` становится глобалом `1`, в скрипт вставляется текст `1+2`).

### 12. Обратные кавычки и комментарии препроцессора

`stripComments` считает строкой только `"..."`. Прогон `` `http://example` `` падает с `unterminated string`: последовательность `//` внутри backticks вырезается до конца строки ещё до лексера. То же сделает `/*` внутри `` `...` `` или `'//'`.

Незакрытый `/*` и в лексере, и в препроцессоре доедает файл до EOF и ошибкой не считается. Скрипт может успешно скомпилироваться без хвоста.

Рекурсия макроса глубже 32 молча оставляет хвост нераскрытым (`#def A A`). `#ifdef` скармливает взятую строку новому `expandStream`, и номер строки в ошибке начинается с 1.

### 13. `self().v += 1` вычисляет объект дважды

`compileModify` для свойства, символьного индекса и вызова идёт в общий хвост: один раз `compileExpr(target)`, потом `store`, который компилирует объект ещё раз.

```419:423:src/compiler.cpp
        uint16_t current = compileExpr(target);
        uint16_t rhs = compileExpr(*expr.kids[1]);
        uint16_t dest = allocTemp();
        emit(binaryOp(expr.binary), dest, current, rhs, 0, 0, expr.line);
        store(target, dest, expr.line);
```

Прогон с нативом `self()`, который возвращает host-объект: на один `self().v += 1` `self` вызывается дважды, `set` — один раз. Чтение и запись могут попасть в разные объекты, если два вызова вернули разное. Для индекса таблицы и для `*p` есть отдельные ветки, которые вычисляют адрес один раз; для `obj.prop`, `s[[i]]` и `var(...)` — нет.

`s[[i]]++` до VM не доходит (`compileUpdate` этот вид цели не принимает). `s[[i]] += 1` доходит.

### 14. Конец `for i = a .. b` зависит от формы выражения

Цифры прогона — в семантике. Причина в компиляторе: локал как правая граница `..` — это сам регистр переменной, глобал и любое вычисление — временный регистр, заполненный один раз. Внутри цикла присваивание локалу `n` раздвигает уже идущий цикл до нового `n`. Запись `(n + 0)` или глобал так не делают.

Границу надо один раз копировать в свой регистр. После починки `Move` эта копия будет честной и для `null`.

### 15. Сравнения с NaN и крайние целые

`gs_log(-1)` даёт NaN. Дальше `compare` трактует «ни меньше, ни больше» как равенство:

```85:93:src/machine.cpp
int Machine::compare(const Value& lhs, const Value& rhs, int line) {
    auto left = asNumber(lhs);
    auto right = asNumber(rhs);
    if (!left || !right) {
        throw Error("comparison expects numbers", line);
    }
    if (left->value < right->value) return -1;
    if (left->value > right->value) return 1;
    return 0;
}
```

Прогон: `n == n` → `0`, `n <= n` → `1`, `n <= 1` → `1`, `n < 1` → `0`. `==` идёт через `equals` и для NaN честно ложен, `<=` / `>=` — нет.

`-2147483648 / -1` бросает `integer overflow`. `-2147483648 % -1` на этом прогоне вернул `0`. В C++ пара непредставима и для `%`; на другой стандартной библиотеке это может быть SIGFPE. Ветка `Mod` ту же проверку, что `Div`, не делает.

`(int)1e20` на этом прогоне дал `2147483647`. Приведение float→int32 вне диапазона в языке не проверяется (арифметика тот же диапазон отвергает). `static_cast<int32_t>(float)` вне диапазона — неопределённое поведение C++, опираться на `2147483647` нельзя. Та же дыра в `asInt` у `gs_*` и в `numberText`.

Каст строки в int через `stoll` с последующим `static_cast<int32_t>` большие значения обрезает молча; `stoll`, который не влез в `long long`, превращается в `0` голым `catch (...)`.

### 16. Повторный `var` ошибкой не является

```94:97:src/compiler.cpp
    void collect(const Stmt& stmt) {
        if (stmt.kind == Stmt::Kind::Var && !locals_.contains(stmt.name)) {
            declare(stmt.name, stmt.line);
        }
```

`declare` умеет бросать `duplicate variable`, но до него не доходят вторые `var`. Прогон `var x = 1; var x = 2;` возвращает `2`. Дублируется только список параметров: там `declare` зовётся напрямую. Параметр и `var` с тем же именем тоже проходят молча и делят один слот.

### 17. `load` оставляет старый мир

Второй `load` меняет байткод функций и не сбрасывает глобалы, пины, нативы и `runStack`. Повторное `int x;` не возвращает начальное значение, если имя уже есть. `#def` того же имени значение перезаписывает. После дефекта 8 в стеке ещё и лежат мёртвые кадры; `load` их не выбрасывает, а индексы функций под ними уже другие.

Неизвестное имя в `CallName` по-прежнему даёт целое `0`, не `null` и не ошибку. Чтение неизвестного имени компилируется в `null`. Два разных «нет такого».
